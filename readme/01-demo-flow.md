# 演示流程

第一次打开项目时，不需要把所有按钮都点一遍。更合适的方式是顺着一条真实业务线，看清楚这个项目解决了什么问题。

## 准备

```bash
bundle config set --local path vendor/bundle
bundle install
bin/rails db:prepare
bin/rails db:seed
bin/dev
```

登录：

```text
demo@launchpulse.test / password
```

示例站点：

```text
/s/neighborhood-coffee
/s/studio-sprint-course
/s/clearleaf-skincare
```

## 第一段：先看清楚产品是什么

进入后台后，先打开任意站点详情页。

可以先说明这几句话：

> 这个项目不是做一个新的拖拽建站器，而是做网站发布后的增长控制台。左边是页面结构，中间是当前站点预览，右边是系统给出的优化建议和正在跑的实验。它解决的是小商家页面上线后不知道怎么改、改了不知道有没有效果的问题。

这时可以停在页面上，先看懂三个区域：

- 左侧：页面区块树，说明页面不是一整块网页代码，而是结构化区块。
- 中间：实时预览，说明后台改动可以立刻看到。
- 右侧：建议和实验，说明增长动作不是孤立按钮。

## 第二段：跑一遍智能建议

点击 `生成诊断`。

可以这样解释：

> 这里的智能建议是确定性输出，不依赖外部接口。这样做是为了保证项目本地能稳定运行，也方便测试。重点不是模型有多强，而是后面的推荐、补丁、实验和发布链路是完整的。

展开一条建议后，重点看：

- 它关联了哪个区块；
- 它指出的问题是什么；
- 它建议改哪些字段；
- 它给了预期影响和置信度；
- 它生成了可执行的区块补丁。

## 第三段：预览和应用补丁

点击 `预览改动`。

此时中间预览应该能看到区块文案变化。这里可以讲：

> 预览不写数据库，只让用户先确认改动。真正点击应用以后，才会更新草稿区块。这样把“看看效果”和“修改草稿”分开，避免用户误操作。

然后点击 `应用到草稿`。

应用后说明：

> 这一步还没有发布到公开站点。公开站点只读取已发布快照，所以后台草稿可以继续调整，不会影响真实访客。

## 第四段：从补丁创建实验

点击 `测试原版和新版` 或对应的实验创建按钮。

这里是项目的一个重点：

> 创建实验时，系统会把补丁应用前的区块数据保存成原版本，把补丁应用后的区块数据保存成推荐版本。两个版本都是完整数据，不是临时差异。这样后面页面继续发布，也不会改变这个实验的基线。

可以打开实验区域，看原版本和推荐版本的信息。

## 第五段：打开公开站点触发真实事件

打开公开站点，比如：

```text
/s/clearleaf-skincare
```

在公开页上提交表单或点击商品结账。

可以说明：

> 公开页会给访客设置稳定的访客标识，然后按实验做分流。表单提交和结账事件会带上区块标识，后端会用它判断这次转化应该算到哪个实验。

如果需要调试访客分流，可以用：

```bash
DEMO_DEBUG=true bin/dev
```

公开页右下角会显示访客短 ID 和当前分配版本。这个只用于本地调试。

## 第六段：回到后台看实时数据

回到站点详情页，看实时事件流和指标卡片。

这里可以讲：

> 事件不是前端假刷出来的。公开页创建事件以后，会进入后台任务做聚合，聚合完成后再通过实时通道刷新看板。这样控制台看到的是后端数据变化，不是本地状态模拟。

重点看：

- 页面浏览量；
- 独立访客；
- 转化率；
- 来源和设备；
- 简单漏斗；
- 实时事件流；
- 实验转化数据。

## 第七段：模拟 1000 个访客

点击 `模拟 1000 位访客`。

可以说明：

> 模拟器不是随机塞一堆无意义数据。它会按来源、设备、实验版本和区块类型生成更接近真实行为的分析事件流，比如商品区会产生商品浏览和结账事件，表单区会产生表单提交事件。

这一步主要展示后台任务和实时看板。

这里要分清楚两条链路：公开表单和公开结账会创建 `Contact`、`FormSubmission`、`Order`、`OrderItem` 这些业务记录；模拟器为了快速撑起看板，只创建分析事件，不创建完整业务对象。

## 第八段：完成实验并应用结果

当实验有数据后，点击完成实验。

然后选择应用推荐版本或保留原版本。

这里要强调：

> 如果推荐版本赢了，草稿区块会更新为推荐版本；如果原版本赢了，系统会把建议标记为被原版本覆盖。A/B 测试不应该只支持“应用新版本”，也要能表达“原版本更好，所以这条建议不采纳”。

## 第九段：发布、对比、回滚

点击 `发布`，生成快照。

然后打开差异页面。

可以讲：

> 发布不是简单保存当前数据库。系统会生成不可变快照，并带校验和。差异页面能看到哪些区块新增、删除、改了哪些字段。回滚时按稳定区块标识恢复，不依赖数据库 id。

最后执行 `回滚`，确认可以恢复历史版本。

## 建议控制时间

如果时间很短，讲：

```text
运行审计 -> 预览补丁 -> 应用草稿 -> 创建实验
-> 公开页提交或结账 -> 后台实时刷新 -> 发布并查看差异
```

如果还想继续看技术细节，再深入：

- 事件接口幂等；
- 转化归因；
- 已发布区块校验；
- 快照校验和；
- 后台任务和实时刷新；
- 测试覆盖。
