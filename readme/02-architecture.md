# 系统架构

这里选择 Rails 单体，不是因为功能简单，而是因为这个项目最重要的复杂度都在同一条业务链路里：页面发布、访客分流、事件采集、转化归因、后台聚合、实时刷新、实验结果、版本回滚。

如果为了“看起来现代”把前后端和任务系统拆得很散，反而很难顺着一条真实请求看完整个流程。Rails 单体的好处是路径短：从公开页面提交事件，到数据库写入，到后台任务聚合，到页面实时刷新，都在同一个工程里能追到。

## 整体结构

系统分成四个运行面：

### 1. 后台控制台

后台控制台给站点运营者使用，主要页面是看板和站点详情页。

后台能做：

- 查看站点和增长分数；
- 查看页面区块；
- 看实时指标；
- 运行智能审计；
- 预览和应用区块补丁；
- 创建和管理实验；
- 发布和回滚快照；
- 模拟访客流量。

### 2. 公开站点

公开站点是访客真正看到的页面，路径是：

```text
/s/:slug
```

公开站点只读取已发布快照，不读取后台草稿。它会设置访客标识，按实验分配版本，并记录页面浏览、点击、表单、结账等事件。

### 3. 事件接口

事件接口用于接收外部上报：

```text
POST /api/v1/events
```

它负责站点令牌校验、参数校验、事件幂等、区块可见性校验和归因处理。

### 4. 后台任务和实时刷新

事件写入后进入后台任务。任务完成聚合以后，通过实时通道刷新后台页面。

这部分对应：

- `AggregateEventJob`
- `Analytics::AggregationService`
- `Analytics::DashboardBroadcaster`

## 为什么公开站点要读发布快照

建站产品里一个很容易出问题的点是：后台草稿和公开页面混在一起。

如果公开页面直接读 `sections` 表，那么用户在后台试改文案，还没点击发布，真实访客就可能看到半成品。LaunchPulse 用 `PublishedSnapshot` 把这件事隔开：

- 后台可以继续改草稿。
- 公开页面只读最后一次发布。
- 发布动作会产生一个不可变版本。
- 回滚也是从历史快照恢复。

对应代码：

- `Sites::PublishedRuntime`
- `Sites::SnapshotService`
- `Public::SitesController`

## 为什么实验版本要保存完整数据

实验创建时，系统会保存两个版本：

- 原版本：补丁应用前的区块数据。
- 推荐版本：补丁应用后的区块数据。

公开页面渲染时，如果访客被分到某个版本，就直接渲染这个版本保存的数据。

这样做是为了避免一个问题：实验跑到一半时，后台又发布了新内容。如果实验原版本继续读取当前快照，那原版本就变了，实验结果就不可信。

对应代码：

- `Experiments::LifecycleService`
- `Experiments::AssignmentService`
- `app/views/public/sites/show.html.erb`

## 为什么后台任务和实时刷新要分开

事件聚合是数据逻辑，页面刷新是展示逻辑。它们不能混在一起。

所以职责拆成：

- `Analytics::AggregationService`：只关心统计和转化。
- `Analytics::DashboardBroadcaster`：只关心怎么刷新后台页面。

这样以后如果要做限流、换实时通道、增加更多页面刷新点，不需要改聚合口径。

## 为什么没有做成前端单页应用

这个项目需要界面，但核心不是复杂前端状态，而是后端业务链路。

使用 Hotwire 的原因是：

- 公开页面和后台预览可以复用服务端渲染；
- 实时指标可以直接替换页面局部；
- 少写一套前端数据缓存；
- 测试更容易覆盖真实请求；
- 更符合 Rails 全栈项目的优势。

如果未来要做完整拖拽编辑器，可以再引入更重的前端状态管理。但当前版本更适合把工程重点放在增长闭环、数据可信度和发布系统上。

## 主要代码分层

- 控制器：接收请求，处理登录、参数、响应。
- 模型：保存业务状态和基础校验。
- 服务对象：承载跨模型的业务流程。
- 后台任务：处理异步聚合和流量模拟。
- 视图组件：按区块类型渲染公开页面和后台预览。
- 测试：覆盖关键边界，不只测正常路径。

这种结构便于阅读：先从页面流程看业务，再从服务对象看核心规则，最后用测试确认边界。
