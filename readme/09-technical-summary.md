# 技术摘要

这份摘要用于快速了解项目的核心工程边界。完整说明可以继续看前面的产品、架构、归因、发布和测试文档。

## 这个项目主要体现什么

LaunchPulse 体现的是：把一个产品问题拆成可运行的 Rails 全栈工程，而不是只做页面和增删改查。

这个项目的主线是网站发布之后的增长闭环：

```text
页面区块 -> 智能审计 -> 建议补丁 -> A/B 实验
-> 访客事件 -> 转化归因 -> 实时看板
-> 应用胜出版本 -> 发布快照 -> 差异对比和回滚
```

这里最值得看的，是这条链路是否完整，以及每个环节的数据边界是否清楚。

## 为什么不是建站器复制品

项目没有做拖拽编辑器，也没有复制任何现有建站器的界面或文案。它做的是建站产品发布之后更容易产生商业价值的一段能力：

- 页面上线后怎么判断转化质量；
- 改动建议怎么变成可执行补丁；
- 补丁怎么进入实验；
- 访客行为怎么进入后台统计；
- 结果怎么回到正式发布版本。

这比单纯复刻一个编辑界面更能体现产品工程判断。

## 关键工程边界

- 公开页面只读已发布快照，不读后台草稿。
- 实验原版本和推荐版本都保存完整渲染数据，后续发布不会改变实验基线。
- 强转化事件不能从公开埋点接口直接伪造，表单和订单必须走受控入口。
- 商品结账必须来自真正展示该商品的商品区块，价格方案结账必须来自价格区块。
- 事件接口使用站点令牌、幂等键和请求指纹，避免重复上报或错 payload 被吞掉。
- 幂等冲突会在创建实验分配之前被拒绝，失败请求不会留下 assignment 副作用。
- 转化归因按显式实验、区块、通用转化三层处理，不把一个转化算到无关实验。
- 聚合服务不反推 assignment，访客分流必须在公开运行时或事件入口完成。
- 订单、表单提交和转化事件有事务边界，避免漏斗断层。
- 发布快照带校验和，回滚前会检查历史版本完整性。

## 技术架构亮点

- Rails 单体承载公开站点、后台控制台、事件接口、后台任务和实时刷新。
- Solid Queue 处理事件聚合和流量模拟。
- Solid Cable 支持后台任务跨进程推送实时更新。
- 服务对象承载核心业务流程，控制器保持相对薄。
- 区块使用结构化数据渲染，便于建议、补丁、实验和发布快照复用。

## 测试和质量保障

项目测试重点不是只测成功路径，而是保护容易出问题的业务边界：

- 草稿不会出现在公开页；
- 实验基线不会漂移；
- 幂等并发冲突会检查请求指纹；
- 公开接口不能伪造强转化；
- 商品和价格结账会校验区块类型；
- 表单提交和事件保持事务一致；
- 转化不会算到错误版本；
- 流量来源和设备分布基于页面浏览；
- 审计不会重复刷出同一条建议；
- 快照差异和回滚可验证。

一键检查命令：

```bash
bin/check-demo
```

## 当前简化边界

这些地方是有意简化，不是遗漏：

- 智能审计是确定性输出，不调用外部模型接口。
- 结账只创建演示订单，没有接真实支付。
- 实验统计是透明近似，不是完整统计平台。
- 权限系统只保留演示所需能力。
- 事件采集是单条写入，已有 Rack::Attack 应用层基础限流；生产环境还需批量上报、采样、网关/多实例共享限流、监控与容量治理。

## 如果进入生产，优先演进什么

1. 接入真实页面导入和编辑能力。
2. 接入外部模型，但保留稳定兜底输出和结构化校验。
3. 增加实验曝光事件、流量分配、人群定向和更严谨统计。
4. 加强账号权限、团队协作、接口密钥轮换和审计日志。
5. 把事件采集升级为批量写入、队列削峰和监控告警。
6. 增加发布审批、预览链接、任意版本对比和单区块恢复。

## 可以继续追的 5 个问题

1. 为什么公开站点要读 `PublishedSnapshot`，而不是直接读后台草稿？
2. 为什么原版本也要保存完整 `props`，不能运行时再读当前快照？
3. 转化归因怎么避免算到无关实验上？
4. 幂等键复用但请求内容变了，接口应该怎么处理？
5. 为什么同一个区块不允许同时存在多个未解决实验？
