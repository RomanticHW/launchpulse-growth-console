# 发布与实验系统

发布和实验是这个项目里最容易被低估的部分。它们看起来只是几个按钮，但背后要解决的是：草稿怎么和正式版本隔离、实验怎么保持稳定、结果怎么安全回到页面、历史版本怎么恢复。

## 草稿和正式版本分开

后台编辑的是草稿。公开页面读的是发布快照。

这个分离很重要。对建站产品来说，用户经常会在后台试改文案、调顺序、预览不同版本。如果公开页面直接读草稿，真实访客就可能看到半成品。

LaunchPulse 的流程是：

1. 后台修改 `Section`。
2. 用户点击发布。
3. 系统生成 `PublishedSnapshot`。
4. 公开页面读取最新快照。

这样后台可以继续改，公开页面仍然稳定。

## 发布快照里保存什么

快照保存的是一个站点在某个时刻的结构化版本：

- 站点信息；
- 页面列表；
- 区块列表；
- 区块类型；
- 区块稳定标识；
- 区块属性；
- 版本号；
- 校验和。

这里没有只保存一条“已发布”状态，因为那样没法对比和回滚。快照让每次发布都有历史记录。

## 为什么需要校验和

回滚依赖历史快照。如果历史快照被手动改坏，回滚会把错误数据写回草稿。

所以每个快照都有校验和。回滚前会重新计算并对比，发现不一致就拒绝回滚。

这不是完整安全系统，但它保护了发布系统最基本的前提：历史版本应该可信。

对应代码：

- `Sites::SnapshotService#publish!`
- `Sites::SnapshotService#rollback!`
- `Sites::SnapshotService#verify_checksum!`

## 差异页面为什么重要

如果只给一段原始结构化数据，技术人员能看，但非技术角色很难理解。差异页面把变化拆成更容易读的内容：

- 新增了哪些区块；
- 删除了哪些区块；
- 哪些区块改了；
- 改了哪些字段；
- 改前和改后分别是什么；
- 原始数据仍然可以展开看。

这说明发布系统不是“保存一下数据”，而是能支持人工确认。

对应代码：

- `PublishingController#diff`
- `app/views/publishing/diff.html.erb`

## 回滚为什么按区块 uid

数据库 id 不适合做长期版本识别。区块可能从导入流程进来，也可能被删除重建，还可能从历史快照恢复。数据库 id 变了，不代表业务上不是同一个区块。

所以回滚按 `section.uid` 匹配。

这样历史快照里的“价格区块”可以恢复到当前草稿里的同一个价格区块，而不是依赖数据库 id 恰好相同。

## 实验创建

实验通常来自一条建议和它对应的区块补丁。

创建实验时，系统会保存：

- 原版本：补丁应用前的数据；
- 推荐版本：补丁应用后的数据；
- 主要转化目标；
- 实验状态；
- 所属区块。

对商品区和价格区，主要转化目标是订单创建；对普通线索场景，主要转化目标是表单提交。

## 访客分流

访客分流不是每次随机。

同一个访客进入同一个实验时，会稳定分到同一个版本。这样用户刷新页面不会一会看到 A，一会看到 B。

分流逻辑基于：

- 访客标识；
- 实验 id；
- 各版本权重。

对应代码：

- `Experiments::AssignmentService`
- `Assignment`
- `Variant`

## 实验结果

实验结果会展示：

- 访客数；
- 转化数；
- 转化率；
- 相对原版本的提升；
- 近似置信度。

这里没有写成严肃统计平台。当前结果适合本地项目观察趋势，不替代完整实验平台。这个边界在文档和代码里都写清楚了。

对应代码：

- `Experiments::ResultsService`

## 应用胜出版本

实验完成后，可以选择推荐版本胜出，也可以选择原版本胜出。

推荐版本胜出时：

- 草稿区块更新为推荐版本；
- 建议标记为已应用；
- 补丁标记为已应用；
- 实验记录胜出版本。

原版本胜出时：

- 草稿区块回到原版本；
- 建议标记为被原版本覆盖；
- 补丁标记为被覆盖；
- 实验记录胜出版本。

这个设计表达了一个重要观点：测试不是为了证明新方案一定好，而是为了做选择。

对应代码：

- `Experiments::LifecycleService#apply_winner!`

## 这部分能体现什么能力

发布与实验系统能体现几个工程点：

- 业务状态流是否清楚；
- 数据快照是否可信；
- 草稿和正式版本是否隔离；
- 实验是否有稳定基线；
- 胜出版本应用是否有明确语义；
- 回滚是否能解释和验证。

这些点都比“页面上有一个发布按钮”更重要。
