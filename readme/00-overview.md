# 产品概览

这个项目的核心很简单：建站产品不应该只停在“把页面搭出来”，还应该帮助用户理解这个页面到底有没有带来业务结果。

对很多小商家来说，网站上线以后才是真正难的地方。页面能访问不代表能转化，按钮有人点不代表能成交，改了文案也不知道是不是变好了。LaunchPulse 就是围绕这类问题做的一个增长控制台。

项目内置了三个示例站点：

- 本地咖啡店：重点是预约、咨询和表单留资。
- 在线课程页：重点是价格方案、课程报名和线索转化。
- 护肤品小电商：重点是商品展示、商品点击和结账转化。

这三个业务看起来不同，但背后的增长链路是一样的：页面区块需要被分析，改动需要被验证，结果需要回到正式发布版本里。

## 这个项目的主要卖点

### 1. 它不是只做后台表格

很多演示项目会停在“后台有列表、详情、创建、删除”。LaunchPulse 的重点不是这些基础能力，而是把一个真实增长场景串起来：

```text
公开站点 -> 访客行为 -> 事件入库 -> 后台聚合 -> 实时看板
-> 智能建议 -> 区块补丁 -> A/B 实验 -> 应用胜出版本 -> 发布快照
```

这条链路里每一步都能在代码和页面里看到，不是只在 README 里描述。

### 2. 它把建站产品里容易被忽略的数据边界做清楚了

比如公开页面只应该看到已发布版本，不能读后台草稿；实验里的原版本不能因为后续发布而变化；一个商品区的结账不应该算到价格区实验；已经从正式页面移除的区块不能继续接收实验数据。

这些点如果不处理，页面看起来也能跑，但数据是不可信的。这里刻意把这些边界做出来，是为了说明项目不只关心界面能不能点，也关心数据含义是否成立。

### 3. 它能被非技术同事先看懂

后台首页能看到站点列表、增长分数和指标。站点详情页能看到页面预览、区块树、建议、实验和实时事件。公开页面可以真实提交表单或点击结账。即使不看代码，也能按演示流程理解“发现问题 -> 尝试改动 -> 验证结果 -> 发布版本”的过程。

### 4. 代码也能继续追问

如果继续看代码，可以追到：

- 发布快照如何生成和回滚；
- 公开站点为什么不读草稿；
- 实验怎么做稳定分流；
- 事件接口怎么做幂等；
- 转化归因怎么避免乱算；
- 后台任务怎么聚合；
- 实时看板怎么跨进程更新；
- 测试怎么覆盖这些边界。

## 没有做什么

当前版本没有把项目写成“全功能建站器”。拖拽编辑器、素材库、域名绑定、支付接入、团队权限、完整统计平台，这些都不是当前版本重点。

当前版本的重点是：用一个可运行的 Rails 项目，把建站产品发布后的增长闭环讲清楚、做完整，并且让代码能经得起追问。

## 当前能力一览

- 后台登录和账号数据。
- 三个示例站点。
- 公开站点渲染。
- 区块组件渲染：首屏、功能网格、评价、联系表单、商品列表、价格方案、常见问题。
- 智能审计和结构化建议。
- 建议补丁预览、应用、回滚、废弃。
- 从建议创建 A/B 实验。
- 访客稳定分流。
- 表单提交和演示结账。
- 事件接口和公开页面事件采集。
- 后台任务聚合。
- 实时事件流和指标刷新。
- 实验结果计算。
- 发布快照、差异对比、回滚。
- 覆盖关键边界的测试。

## 适合怎么看

建议先跑一遍完整业务流程，再看代码。因为这个项目的价值不在单个文件，而在多个模块之间是否对得上：

- 页面区块的稳定标识，能不能贯穿发布、实验和归因；
- 实验创建时保存的数据，能不能保证后续渲染稳定；
- 事件采集和后台聚合，能不能支持实时看板；
- 测试是不是覆盖了真实会出问题的边界。

如果只看控制器和模型数量，很容易低估这个项目；如果沿着一条转化链路追下去，会更容易看出设计取舍。
