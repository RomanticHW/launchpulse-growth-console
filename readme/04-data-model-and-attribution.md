# 数据模型与转化归因

数据模型围绕页面版本和访客转化两类信息组织。页面区块需要跨发布、实验和恢复保持稳定关联；访客事件则需要准确归到对应站点、区块和实验版本。

## 账号与站点

- `Account`：账号；
- `User`：用户；
- `Membership`：用户与账号的关系及角色；
- `Site`：站点；
- `Page`：页面；
- `Section`：页面区块；
- `PublishedSnapshot`：已发布版本；
- `ApiKey`：Events API 密钥。

`Site.slug` 全局唯一。公开路由只根据 slug 查找已发布站点，因此不能允许不同账号使用相同公开地址。

## 稳定业务标识

`Section.uid` 用于跨模块识别同一个页面区块。数据库编号可能因导入、重建或历史恢复而变化，`uid` 则保持稳定。

以下数据都使用区块 `uid` 建立关联：

- 已发布版本；
- 公开页面事件；
- 实验可见性；
- 转化归因；
- 历史版本恢复。

表单字段和商品同样使用稳定 `key`。展示名称可以修改，但提交数据和购买路径不随文案变化。

## 表单与订单

- `Form`、`FormField`：表单及字段配置；
- `Contact`：联系人；
- `FormSubmission`：表单提交记录；
- `Product`：商品；
- `Order`、`OrderItem`：订单及订单项。

公开表单提交会在同一事务中创建联系人、提交记录和事件。商品或课程方案选择会创建示例订单和相应事件。任一步骤失败时，业务记录和事件会一起回滚。

## 事件与聚合

- `Event`：原始访客事件；
- `EventRollup`：聚合统计；
- `Assignment`：访客的实验版本分配；
- `Conversion`：归入实验的转化记录。

事件类型包括页面浏览、按钮点击、表单开始填写、表单提交、商品浏览、结账点击和订单创建。

实验主转化支持：

- `form_submit`
- `order_created`
- `any_conversion`

`checkout_click` 属于操作事件，不代表订单已经创建，因此不会单独写入 `Conversion`。

## 元数据

事件 `metadata` 的顶层必须是 JSON 对象，对象内部可以包含数组或嵌套对象。

`Events::MetadataSanitizer` 会限制：

- 总大小；
- 嵌套深度；
- 每层键数量；
- 不支持的数据类型。

公开站点和 Events API 共用相同的清洗规则。历史异常数据进入聚合时会按空对象处理，避免中断后台任务。

## 转化归因顺序

### 1. 显式归因

事件同时提供 `experiment_id` 和 `variant_key` 时，只归入指定实验版本。系统会检查实验、版本、站点和已发布区块是否一致。

### 2. 区块归因

事件提供 `section_uid` 时，只归入该区块的实验。商品区订单不会计入其他区块的实验。

### 3. 通用转化

事件没有实验和区块信息时，系统会检查访客已有的实验分配，并且只记录目标类型匹配的实验。

聚合服务不会反向创建实验分配。`Assignment` 必须在公开页面渲染或事件写入阶段产生。

## 页面浏览

一个页面可能同时包含多个实验区块，因此页面浏览事件不会直接绑定单个实验。事件元数据会保留本次页面使用的版本分配，便于调试和分析。

## 幂等与请求指纹

Events API 支持 `idempotency_key`。系统还会根据事件类型、访客、来源、设备、页面、区块、实验、时间和清洗后的元数据计算请求指纹。

- 相同键和相同内容：返回已有事件；
- 相同键但内容不同：拒绝请求。

带幂等键的请求会在 PostgreSQL advisory lock 内检查已有事件。冲突检查早于实验分配和事件创建，失败请求不会留下多余的 `Assignment`。

带幂等键的历史事件如果缺少请求指纹，系统会拒绝复用该键。
