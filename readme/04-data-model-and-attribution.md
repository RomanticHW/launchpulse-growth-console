# 数据模型与归因

这个项目的数据模型主要围绕两个问题设计：

1. 页面结构怎么稳定地跨发布、实验和回滚。
2. 访客转化怎么准确算到对应实验上。

如果这两件事没做清楚，页面和图表都可以做得很好看，但数据没有可信度。

## 站点结构

核心模型：

- `Account`：账号。
- `User`：用户。
- `Membership`：用户和账号关系。
- `Site`：站点。
- `Page`：页面。
- `Section`：页面区块。
- `PublishedSnapshot`：发布快照。
- `ApiKey`：事件接口密钥。

页面拆成区块，是因为增长建议、实验和归因都需要落到具体位置。一整页网页代码很难回答“这次转化是不是价格区改动带来的”。

## 区块稳定标识

每个区块有 `uid`。这个字段非常重要。

数据库 id 只适合当前数据库内部使用，不适合跨快照长期识别。区块可能被重新导入、重新排序、从历史快照恢复，数据库 id 都可能变化。但业务上仍然需要知道“这是同一个首屏区块”或“这是同一个价格区块”。

所以：

- 发布快照记录区块 uid；
- 回滚按 uid 匹配区块；
- 事件上报带 section_uid；
- 实验绑定的区块通过 uid 做可见性校验；
- 公开页面分流也按 uid 找对应实验。

这类稳定标识在建站产品里很常见，但很多演示项目会忽略。这里刻意把它做出来，是为了让版本系统和实验系统能接起来。

## 表单和商品也需要稳定标识

表单字段有 `key`，商品有 `key`。

原因类似：

- 表单字段文案可以从“团队人数”改成“公司规模”，但提交数据里的字段名不能跟着变。
- 商品展示名可以改，但公开结账路径不能因为名字变化失效。

对应模型：

- `Form`
- `FormField`
- `FormSubmission`
- `Contact`
- `Product`
- `Order`
- `OrderItem`

这些设计让演示站点不只是展示页面，还能模拟真实留资和下单链路。

## 事件模型

事件分两层：

- `Event`：原始行为。
- `EventRollup`：聚合后的统计。

支持的事件包括：

- 页面浏览；
- 按钮点击；
- 表单开始填写；
- 表单提交；
- 商品浏览；
- 结账点击；
- 订单创建。

原始事件保留详细上下文，聚合表用于后台快速展示指标。

实验主转化目前只支持：

- `form_submit`
- `order_created`
- `any_conversion`

`checkout_click` 会作为交互事件保留在事件流里，但不作为实验主转化。原因是商品和价格方案结账最终都会产生 `order_created`，用订单创建作为主转化更清楚。

`Conversion` 表也只允许这三种口径。页面浏览、按钮点击、商品浏览、结账点击都可以进入 `Event`，但不会作为 `Conversion` 记录保存。

事件的 `metadata` 顶层必须是对象。对象里面可以包含数组，比如活动标签、商品列表或调试字段，但不能把数组或字符串直接作为顶层 metadata 写入事件。

这样做不是形式要求，而是为了让后续聚合逻辑能稳定读取 `section_uid`、`form_id`、`product_key` 这类业务字段。公开页面和外部事件接口都会走同一套清洗规则；历史脏数据进入聚合时也会被当作空对象处理，不会让后台任务中断。

## 为什么不能把转化算到所有实验

假设一个访客同时参加了三个实验：

- 首屏文案实验；
- 商品区实验；
- 价格区实验。

这个访客最后在商品区完成了结账。

如果系统把这次结账同时算到三个实验里，图表会很好看，但结论是错的。商品区结账更应该归到商品区实验，除非这次事件没有任何区块信息，才可以作为更宽泛的转化处理。

所以这里做了三层归因规则。

## 转化归因规则

### 第一优先级：显式归因

如果事件已经带了实验和版本，就只算这个实验。

这适合外部系统已经明确知道当前访客暴露在哪个实验版本下的情况。

### 第二优先级：区块归因

如果事件带了 `section_uid`，系统会找这个区块对应的活跃实验，只给这个实验记转化。

这适合公开页面上的表单、商品、价格方案等具体行为。

assignment 会在公开运行时或事件入口创建，聚合服务只消费已经发生的暴露和事件，不会在后台按 `section_uid` 反推出一次新的分流。

### 第三优先级：通用转化

如果事件没有实验，也没有区块，只能作为通用转化处理。系统可以给访客已经参加的活跃实验计数，但不会把事件本身强行改写成某个实验。

这避免了一个常见错误：把无法归因的事件硬塞给第一个实验，导致后续分析误判。

通用转化还会再看实验目标：`order_created` 只会写入订单目标或 `any_conversion` 实验，`form_submit` 只会写入表单目标或 `any_conversion` 实验。这样数据库里的转化记录本身也是干净的，不需要只靠结果服务再过滤一遍。

对应代码：

- `Analytics::AggregationService`
- `Conversion`
- `Assignment`

## 页面浏览为什么不直接归因

页面浏览比较特殊。一个页面可能同时包含多个正在实验的区块。如果把页面浏览直接归到某个实验，就会让曝光和转化口径混乱。

所以公开页面浏览会记录本次访客分到的版本信息，但事件本身不绑定某个实验。

这份信息存在事件附加数据里，方便排查和观察，但不会污染实验归因。

当前公开运行时只开放首页 `/s/:slug`。模型里保留了 `Page` 和 `page_path`，但多页公开站点还需要把区块可见性扩展成按路径判断。

## 幂等为什么要加指纹

外部事件接口支持幂等键。只有幂等键还不够，因为调用方可能错误地复用了同一个键，却换了事件内容。

比如第一次是页面浏览，第二次变成订单创建。如果系统只看幂等键，就会静默返回第一次事件，第二次真实转化就丢了。

所以事件增加了请求指纹：

- 同一个键、同一个内容：返回已有事件。
- 同一个键、不同内容：拒绝请求。

这里还有一个容易被忽略的顺序：接口会先检查幂等键和请求指纹，再做实验归因和访客分配。

原因是归因本身会产生副作用，比如给访客创建实验 assignment。如果一个重复请求最终会因为指纹不一致被拒绝，就不应该在拒绝之前留下新的实验分配记录。这个顺序让“失败请求不污染实验数据”这件事更容易解释，也更容易用测试保护。

通过事件接口创建 assignment 和 Event 也在同一个事务里完成。即使请求没有传幂等键，事件创建失败也不会留下半条访客分流数据。

带幂等键的事件必须保存 `payload_fingerprint`。如果历史脏数据缺少这个指纹，系统会拒绝复用这个幂等键，而不是把新的请求内容当成旧事件返回。

对应代码：

- `Events::PayloadFingerprint`
- `Events::IngestionService`

## 归因设计体现什么

这部分不是为了显得模型多，而是为了让项目数据可信：

- 稳定标识保证页面、实验、发布能接起来；
- 归因顺序保证转化不会乱算；
- 幂等指纹保证外部上报不会静默污染数据；
- 测试覆盖这些边界，避免后续改动破坏。
