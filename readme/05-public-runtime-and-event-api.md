# 公开站点与事件接口

公开站点是这个项目最重要的运行面之一。后台控制台展示的是配置和结果，公开站点才是真正产生访客行为的地方。

这里提供了两套入口：

- 公开页面自己的事件采集。
- 外部系统可以调用的事件接口。

这样既能模拟建站产品自带的埋点，也能说明以后接第三方页面或独立前端时，后端接口怎么保持数据一致。

## 公开站点路由

```text
GET  /s/:slug
POST /s/:slug/events
POST /s/:slug/forms/:form_id/submissions
POST /s/:slug/products/:product_key/checkout
POST /s/:slug/plans/:plan_key/checkout
```

这些路由负责：

- 渲染公开页面；
- 记录点击等轻量事件；
- 处理表单提交；
- 处理商品演示结账；
- 处理价格方案演示结账。

## 公开页面怎么渲染

公开页面不会直接读取后台草稿，而是读取最新发布快照。

当前 demo 的公开路由只服务首页 `/s/:slug`。如果后续开放多页面，需要把区块可见性校验扩展成按页面路径判断。

渲染规则是：

1. 如果访客没有参加某个区块实验，就渲染发布快照里的区块数据。
2. 如果访客参加了实验，就渲染被分配版本保存的数据。

这里有一个关键点：原版本也要读取实验创建时保存的数据，而不是读取当前快照。

原因是实验跑起来以后，后台可能继续发布页面。如果原版本跟着当前快照变化，实验基线就变了。看起来还是 A/B 测试，实际上已经不是同一组对比。

对应代码：

- `Sites::PublishedRuntime`
- `Public::SitesController`
- `app/views/public/sites/show.html.erb`

## 表单提交

联系表单不是写死字段，而是根据后台配置的字段渲染。

字段有稳定 key。比如展示文案从“团队人数”改成“公司规模”，提交数据里的 key 仍然可以保持 `headcount`。这样历史数据不会因为文案变化失去意义。

提交成功后会创建：

- 联系人；
- 表单提交记录；
- 表单提交事件；
- 后台聚合任务。

如果邮箱不合法、必填字段缺失，相关记录都不会创建。

对应代码：

- `Public::FormSubmissionsController`
- `Form`
- `FormField`
- `FormSubmission`
- `Contact`

## 演示结账

商品区和价格区都可以触发演示结账。

当前没有接真实支付，因为当前项目重点不是支付系统，而是转化链路。结账会创建演示订单，并记录两个事件：

- 结账点击；
- 订单创建。

这两个事件和订单在同一个事务内创建。也就是说，如果事件创建失败，订单也不会留下来。这样后台漏斗不会出现“有订单、没转化事件”的断层。

`checkout_click` 是交互事件，真正用于实验主转化的是 `order_created`。这样价格区和商品区都能用同一套订单转化口径。

按钮点击、商品浏览、表单开始填写也都只是行为事件，不会写入 `Conversion` 表。`Conversion` 只表示表单提交、订单创建，或者显式的通用转化口径。

对应代码：

- `Public::CheckoutsController`
- `Product`
- `Order`
- `OrderItem`

## 公开事件采集

公开页面上的按钮、商品、表单会尽量带上区块标识。

后端收到事件后，会先判断这个区块是否仍在已发布页面里。如果区块只是后台草稿，或者已经从发布版本里移除，就不能继续创建实验数据。

这个校验看起来比较严格，但对实验数据很重要。否则用户从旧页面、脚本或恶意请求里传一个草稿区块标识，也能污染实验结果。

对应代码：

- `Public::EventsController`
- `Public::BaseController`
- `Events::MetadataSanitizer`

## 外部事件接口

接口路径：

```text
POST /api/v1/events
```

示例请求：

```json
{
  "site_token": "signed-token",
  "event_type": "order_created",
  "visitor_id": "visitor-123",
  "session_id": "session-123",
  "source": "search",
  "device": "mobile",
  "section_uid": "section-uuid",
  "idempotency_key": "event-123",
  "metadata": {
    "order_total": "49.00"
  }
}
```

接口会做这些事情：

1. 校验站点令牌。
2. 校验事件类型、来源、设备。
3. 清洗附加数据，限制大小和嵌套深度。
4. 如果带了区块标识，确认区块仍在已发布快照里。
5. 如果带了实验和版本，确认它们属于同一个站点和实验。
6. 处理幂等键和请求指纹。
7. 创建事件。
8. 入队后台聚合任务。

## 附加数据为什么要清洗

事件接口的附加数据是开放输入。如果不限制，调用方可以传很深的嵌套、非常大的内容，或者不能正常转成结构化数据的对象。

所以这里做了统一清洗：

- 控制总大小；
- 控制嵌套深度；
- 控制每层 key 数；
- 把参数对象转成普通哈希；
- 对不支持的对象做字符串化处理。

公开页面和外部接口都使用同一套逻辑，避免两边行为不一致。

公开页自动补上的 `section_uid`、`form_id`、`product_key` 也会先和业务 metadata 合并，再统一清洗后入库。它们虽然通常来自页面自身，但公开入口不能假设任何参数天然可信。

## 错误处理

常见错误包括：

- 令牌无效；
- 事件类型不支持；
- 来源或设备不合法；
- 区块不在已发布页面里；
- 实验版本不匹配；
- 附加数据过大或过深；
- 幂等键对应了不同请求内容。

这些错误会返回结构化响应，方便调用方定位问题。
