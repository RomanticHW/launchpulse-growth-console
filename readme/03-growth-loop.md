# 页面优化与实验流程

LaunchPulse 将页面分析、内容调整、实验验证和版本发布组织为一套连续流程。

```text
页面区块 -> 优化建议 -> 内容补丁 -> 草稿预览
-> A/B 实验 -> 访客分流 -> 转化归因
-> 选择实验版本 -> 发布记录
```

## 页面区块

页面由结构化区块组成。不同区块分别保存标题、按钮、卖点、表单、商品、价格和问答等内容。

每个区块都有稳定的 `uid`，用于关联：

- 发布版本；
- 优化建议；
- 内容补丁；
- A/B 实验；
- 访客事件；
- 转化归因；
- 历史版本恢复。

## 页面分析

当前分析服务根据区块类型和内容规则生成建议，不调用外部服务。建议内容包括：

- 需要调整的区块；
- 当前问题；
- 调整依据；
- 建议字段；
- 重点观察指标；
- 参考置信度。

重复分析不会为相同区块和标题创建多条未处理建议。

## 内容补丁

每条建议都会创建 `SectionPatch`，并保存：

- `before_props`：修改前内容；
- `after_props`：修改后内容；
- `props_diff`：发生变化的字段；
- 当前处理状态。

预览只读取补丁内容，不修改数据库。应用和撤回只更新当前草稿，不会改写补丁中保存的前后版本。

## A/B 实验

实验创建时会固定保存原始版本和优化版本的完整区块数据。公开站点根据访客编号和实验编号进行稳定分流，同一访客刷新页面后仍会看到相同版本。

同一区块只能有一个未处理完的实验，避免多个版本同时影响渲染和归因。

## 事件与归因

公开页面尽量为交互事件附带 `section_uid`。表单提交和订单创建会通过受控入口生成业务记录和事件。

转化归因按以下顺序处理：

1. 事件明确指定实验和版本时，使用显式归因；
2. 事件带区块标识时，归到该区块的实验；
3. 缺少实验和区块信息时，按通用转化规则处理。

这种顺序可以避免商品区订单被同时计入首屏或价格区等无关实验。

## 应用实验结果

实验结束后可以采用原始版本或优化版本。所选内容会写入当前草稿，相关建议和补丁状态也会同步更新。

采用实验结果不会自动发布。运营人员仍需确认草稿并执行发布，公开站点才会使用新内容。

## 发布记录

发布会生成不可变的结构化版本，并保存版本号、内容和校验和。版本记录支持内容差异对比和历史恢复。

恢复历史内容时，系统会将其写入草稿并发布为一个新版本，因此后续仍可追踪恢复操作发生的时间和结果。
