# 增长闭环

LaunchPulse 最想表达的是一条闭环，而不是一组孤立功能。

这条闭环是：

```text
页面区块
-> 智能审计
-> 增长建议
-> 区块补丁
-> 预览和应用
-> A/B 实验
-> 访客分流
-> 行为事件
-> 转化归因
-> 实验结果
-> 应用胜出版本
-> 发布快照
-> 差异对比和回滚
```

如果只做其中一两步，项目会很像普通后台功能。真正有价值的是：每一步都能把数据传给下一步，而且不会把业务含义弄乱。

## 页面区块是增长动作的最小单位

页面没有作为一整段网页代码存起来，而是拆成区块。每个区块有类型和属性，比如：

- 首屏区块：标题、副标题、按钮文案。
- 功能区块：卖点列表。
- 表单区块：字段配置。
- 商品区块：商品列表和结账入口。
- 价格区块：方案、价格和按钮。
- 常见问题区块：问题和回答。

这样做的原因是：增长建议通常不是针对整页，而是针对某个具体区块。比如“首屏价值主张不清楚”“价格区按钮不够明确”“表单字段太多”。区块化以后，建议、补丁、实验、归因都能落到同一个单位上。

## 智能审计不是一句建议，而是结构化结果

审计结果会落到这些数据上：

- 哪个区块有问题；
- 问题是什么；
- 建议改哪些字段；
- 预期影响；
- 置信度；
- 可执行补丁。

当前智能审计是确定性输出，不调用外部模型。这个取舍是有意的：项目在不同机器上都应该能稳定跑通，测试也能精确断言输出内容。真实产品可以接外部模型，但当前版本先把后面的工程链路打通。

对应代码：

- `Ai::GrowthAuditService`
- `AiAudit`
- `AiFinding`
- `Recommendation`

## 区块补丁保留证据

建议落地以后，会生成 `SectionPatch`。

补丁里保存：

- 改之前的区块数据；
- 改之后的区块数据；
- 当前状态。

这看起来只是多存了两份结构化数据，但它解决了一个真实问题：后面如果要做实验，必须知道“原版本到底是什么、推荐版本到底是什么”。如果只保存当前区块数据，过几天再看就说不清当时测试的内容了。

所以补丁在这里是证据，而不是临时变量。应用、回滚、实验状态变化，都不能重写这两份证据。

对应代码：

- `SectionPatch`
- `SectionPatchesController`
- `Experiments::LifecycleService`

## 实验不是简单切换文案

创建实验时，会生成两个版本：

- 原版本：来自补丁应用前的数据。
- 推荐版本：来自补丁应用后的数据。

两个版本都保存完整区块数据。公开页面渲染时，如果访客有实验分配，就直接用被分配版本的数据。

这保证了实验稳定性。否则后台如果继续发布新快照，原版本可能跟着变化，实验就不再是同一次对比。

对应代码：

- `Experiment`
- `Variant`
- `Assignment`
- `Experiments::AssignmentService`
- `app/views/public/sites/show.html.erb`

## 事件要能回到具体区块

访客在公开页面上做的行为，会尽量带上区块标识。

比如：

- 点击首屏按钮：带首屏区块标识。
- 提交联系表单：带表单区块标识。
- 点击商品结账：带商品区块标识。
- 点击价格方案：带价格区块标识。

这样后台在计算转化时，才能知道这次转化应该算到哪个实验，而不是直接算到访客参加过的第一个实验。

对应代码：

- `Public::BaseController`
- `Public::EventsController`
- `Public::FormSubmissionsController`
- `Public::CheckoutsController`
- `Analytics::AggregationService`

## 结果要能回到页面

实验完成后，系统支持两种结果：

### 推荐版本胜出

说明这次建议有效，草稿区块更新为推荐版本，建议标记为已应用。

### 原版本胜出

说明这次建议没有赢，草稿区块回到原版本，建议标记为被原版本覆盖。

这里保留了第二种情况。真实的增长系统不能默认“新建议一定更好”，否则 A/B 测试就只是一个形式。

对应代码：

- `Experiments::LifecycleService#apply_winner!`
- `Experiments::ResultsService`

## 发布把结果固化

草稿改完以后，还要发布成快照。快照是公开页面真正读取的版本。

发布以后可以：

- 查看差异；
- 回滚到历史版本；
- 校验历史快照没有被篡改。

这让增长动作有一个收口：不是改完页面就结束，而是把验证后的结果进入正式版本管理。

对应代码：

- `Sites::SnapshotService`
- `PublishingController`
- `app/views/publishing/diff.html.erb`

## 这条闭环能说明什么

这条链路最值得看的地方，是每一步是否经得起追问：

- 建议能不能变成真实改动；
- 改动能不能进入实验；
- 实验能不能收集真实事件；
- 事件能不能正确归因；
- 结果能不能回写页面；
- 页面能不能安全发布和回滚；
- 这些边界有没有测试保护。

这比单独展示一个“增长建议按钮”或一个“图表页面”更能说明工程完整性。
