# 限制与后续路线

这个项目不适合描述成“已经可以直接上线卖给客户”的完整产品。它现在更准确的定位是：一个可以本地运行、业务链路完整、关键边界有测试保护的 Rails 产品工程样例。

权限方面：已有 `owner` / `marketer` / `viewer` 基础分工（viewer 只读；模拟流量与 token 轮换限 owner；写操作允许 owner/marketer）。仍没有完整团队协作、邀请流和细粒度资源策略。公开写面有 Rack::Attack 限流，但不是完整的滥用防护体系。

下面这些限制需要说清楚，因为它们也是判断工程成熟度的一部分。

## 当前限制

### 1. 智能建议是确定性输出

当前智能审计不调用外部模型接口，而是根据区块类型和页面内容生成稳定建议。

这样做的原因：

- 本地运行不需要密钥；
- 测试结果稳定；
- 不会因为网络或额度影响演示；
- 后续推荐、补丁、实验、发布链路可以稳定验证。

限制也很明确：它不是一个真正能理解所有行业页面的模型。生产版本可以接外部模型，但仍然应该保留一个稳定 fallback，避免核心流程完全依赖第三方。

### 2. 结账是演示订单

当前商品和价格方案结账只创建演示订单，不接真实支付。

生产版本需要增加：

- 支付平台；
- 支付回调；
- 回调幂等；
- 订单状态机；
- 退款和取消；
- 金额、币种、税费、优惠券；
- 异常支付状态处理。

当前版本只负责把“订单创建”作为转化事件接入实验和分析系统。

另外，`模拟 1000 位访客` 模拟的是分析事件流，不会为每个模拟转化创建 `Contact`、`FormSubmission`、`Order`、`OrderItem`。真实公开表单和公开结账会创建这些业务对象；模拟器的定位是快速验证后台任务、聚合和实时看板。

### 3. 实验统计是透明近似

当前实验结果能展示访客数、转化数、转化率、提升比例和近似置信度。

这足够说明数据流和结果计算，但不是完整实验平台。

生产版本还需要：

- 样本量策略；
- 实验曝光事件；
- 延迟转化窗口；
- 访客身份合并；
- 分层分析；
- 互斥实验组；
- 逐步放量；
- 更严谨的统计检验。

### 4. 权限系统保持简单

当前账号和登录足够支撑项目演示，但生产版本需要更完整的权限体系：

- 角色权限；
- 邀请和成员管理；
- 账号隔离审计；
- 接口密钥轮换；
- 操作日志覆盖；
- 会话安全策略。

### 5. 事件写入还不是大规模采集架构

当前事件接口以单条写入为主。

生产版本可以继续扩展：

- 批量上报；
- 请求压缩；
- 网关与多实例共享限流（当前已有 Rack::Attack 应用层基础限流）；
- 采样；
- 队列削峰；
- 死信队列；
- 事件版本；
- 数据仓库同步；
- 监控、告警和容量治理。

公开表单和结账会先把业务记录与 `Event` 写入同一个事务，再直接入队聚合任务。这个设计足够支撑演示链路，但还不是完整 outbox；生产环境应该增加可靠消息表或定期 backfill，把 `aggregated_at` 为空的事件重新入队，避免提交成功但入队失败后长期漏聚合。

当前版本提供了一个手动演示辅助任务：

```bash
bin/rails launch_pulse:enqueue_unaggregated_events
```

它只会把 `aggregated_at` 为空的事件重新入队，方便本地演示时说明恢复边界。它不是完整 outbox，也不会自动运行。

## 后续路线

### 第一阶段：把站点导入做得更像真实产品

当前示例站点来自 seed。下一步可以做：

- 从 URL 抓取简单页面；
- 把网页内容转成区块结构；
- 支持用户手动调整区块；
- 支持图片区块和素材管理；
- 支持移动端预览更细的断点。

这会让项目更接近真实建站产品的入口。

### 第二阶段：增强智能建议

后续可以接外部模型，但要注意工程边界：

- 提示词版本管理；
- 输出结构校验；
- 失败重试；
- 成本记录；
- 建议去重；
- 人工编辑建议；
- 保留确定性 fallback。

模型调用不应该直接塞进控制器，而是继续让建议落到结构化数据和补丁上。

### 第三阶段：增强实验平台

可以补：

- 实验曝光事件；
- 流量比例调整；
- 人群定向；
- 定时开始和结束；
- 多实验互斥；
- 守护指标；
- 实验决策记录；
- 实验归档。

这些会让项目从“增长闭环样例”更接近真实实验平台。

### 第四阶段：增强分析看板

可以补：

- 日期范围；
- 渠道下钻；
- 设备和浏览器分析；
- 漏斗编辑器；
- 分群；
- 导出；
- 异常检测；
- 更细的事件列表筛选。

当前看板已经能说明实时数据链路，后续重点是分析深度。

### 第五阶段：增强发布治理

可以补：

- 发布审批；
- 预览链接；
- 任意两个版本对比；
- 定时发布；
- 回滚原因；
- 发布日志；
- 单个区块恢复。

这会让发布系统更像团队协作产品，而不是单人后台。

## 当前版本主要体现什么

当前版本重点体现的不是功能数量，而是：

- 把一个产品问题拆成可运行链路。
- 处理发布、实验、归因这种跨模块状态。
- 为数据可信度设计边界。
- 用测试保护真实业务风险。
- 明确哪些能力只是当前简化，哪些进入生产前必须继续加固。

继续看技术细节时，可以从这几个方向追：

- 公开页面为什么不读草稿；
- 实验原版本为什么必须保存完整数据；
- 转化归因为什么不能直接遍历所有实验；
- 幂等键为什么还需要请求指纹；
- 回滚为什么不能只靠数据库 id；
- 后台任务和实时刷新为什么要拆职责。

这些问题比“用了哪些 gem”更能看出项目的工程判断。
